## 0. この文書の位置づけ

「施策管理表（Excel）」と「KPI・PDCA管理アプリ」の**二重管理をやめ、施策管理表の機能をアプリ側にも持たせて、PDCA・KPI管理と一体で運用できるようにする**ための設計提案です。実装は未着手で、本方針の承認後に段階的に進めます。

**結論：可能です。** 施策管理表（UN/SCH/MED/IS各シート・A〜]列・最大4組のKPI/目標/実績）を、アプリ内で新規追加・編集・削除でき、**Excelともアプリともどちらをメインにしてもよい相互同期**、**Teams通知によるフォロー**、**Boxへの自動バックアップ（更新時＋日次）**、そして維持したい機能（複数ソート・見出し色・Backlogリンク）を備えた形にできます。

## 2. 現状の課題（今回いただいた内容の整理）

### 【運用】PDCAが定着しない
1. PDCAを回して戦略・施策の目的/目標達成に近づくフローが定着しない。
2. どうPDCAを回し、何を検証すればよいか具体化できない。
3. PDで止まっている施策のうち、**そこで完了でよいもの**と、**PDCAを（複数回でも）回すべきもの**の仕分けができていない。
4. 実績数値の記入が定着しない。

### 【施策管理表の機能】
5. 記入の仕方が統一されず、二次利用時にデータの不揃いがネックになる。
6. 横長すぎて1施策ごとの閲覧性が悪い。
7. バックアップ機能がない。

### 【要望】
8. Excelでもアプリでも、人によって使いやすい方をメインにできるようにしたい。
9. 通知などで「忘れない・遅れない」フォローをしたい。

### 【維持したい（施策管理表の機能）】
10. 複数ソート（Excelのソート機能）
11. 書式（見出しセルの色：1行目と2行目）
12. リンク設定（M列 Backlog課題へのリンク）

## 3. 課題・要望への対応方針（提案）

### A. PDCA定着（課題1〜4）— アプリが「回し方」の足場になる

単なる表ではなく、**PDCAの手順を画面が誘導する**設計にします。

- **施策タイプの仕分け（課題3）**：各施策に「**単発完了型／継続改善型**」の区分を持たせます。判定ガイド（例：目標が一度きりの実施で達成なら単発完了型／CVR改善など継続的に伸ばす目標なら継続改善型）を選択時に表示。**PDで止まっている施策を「要仕分け」リストに自動抽出**し、「完了にする／PDCAを継続する」をその場で選べるようにします。
- **PDCAの回し方の具体化（課題1・2）**：施策編集画面から「この施策のPDCAを設計」を押すと、**検証テンプレート**（①検証で見る指標＝施策のKPIから自動候補、②判定基準＝目標達成/未達のライン、③次アクション＝Act）が空欄で出て、埋めるだけでPDCA1サイクルが定義できます。継続改善型は**2サイクル目以降を自動で促し**、前回の実績→今回の目標へ引き継ぎます。
- **検証項目の標準化（課題2）**：施策種類（記事/メルマガ/WP/LP改善…）ごとに「よく見る指標」の候補を用意し、検証項目を選ぶだけにします（自由記入も可）。
- **実績記入の定着（課題4）**：検証日を過ぎた施策の実績欄を**必須化**し、未記入は後述のアラート＋Teams通知でフォロー。「実績未記入」「PDCA停滞（検証日超過なのに次サイクル未設定）」を一覧で可視化します。

### B. 記入統一・二次利用（課題5）

- 大分類・手法・施策種類・ステータス等は**「リスト」シート由来のプルダウン**からの選択に統一（自由入力は例外扱い）。
- 取込・保存時に**表記ゆれ・必須未入力・日付形式**を検査し、崩れを警告。
- これにより、二次利用（集計・分析・KPI連携）時のデータ不揃いを防ぎます。

### C. 閲覧性（課題6：横長問題）

- **1施策＝1カードの詳細ビュー**を用意し、横スクロールなしで1件を一望（基本情報／日付／ステータス／4組KPI／Backlogリンクをカード内に整理）。
- 一覧は**必要な列だけ表示＋列の表示ON/OFF**を可能にし、横長を解消。検索・フィルタと併用。

### D. バックアップ（課題7）

- **更新時バックアップ**：保存/マージのたびに、変更前スナップショットをBoxへ日時付きで自動退避（誤マージ・誤上書きから復旧可能）。
- **日次バックアップ**：1日1回、定期実行タスクで当日分のスナップショットをBoxへ自動保存。
- **世代管理・保持ルール**（案）：日次は直近30日分を保持、それ以前は月初版のみ残す等（世代数は運用に合わせ調整）。
- 復旧はBox上の日時フォルダから任意時点のJSON/Excelを選ぶだけ。

### E. 両方メイン（要望8）— 同期モデル2をガードレール付きで

Excelとアプリのどちらをメインにしてもよい**施策No.単位の相互マージ**を実装します。

- 各施策に**「最終更新日時」を自動付与**（Excelにも列として出力／取込時に読取）。No.＋最終更新日時で行単位に統合。
- **施策No.は一意・不変をルール化**（アプリが自動採番。例 `MED-013`）。手動改番は禁止。
- **同一施策が両方で更新**されていた場合は**「競合解決画面」でExcel版/アプリ版を1件ずつ選択**（無言上書きはしない）。
- **削除は即時確定せず「削除候補」フラグ**にして確認後に確定（誤消し防止）。
- マージ前に必ずBoxへバックアップ（D参照）。

> ⚠️ 制約：これは「取込時にNo.単位で自動統合する」方式で、リアルタイム同期ではありません。**同じ行を複数人が同時にリアルタイム編集**するには別途クラウドDB化が必要で、単一HTMLの範囲外です。

### F. 通知フォロー（要望9）— Teams

- **アプリ内アラート**：起動時に「検証日が近い／超過」「実績未記入」「PDCA停滞」「要仕分け（PD止まり）」をダッシュボード上部に強調表示。
- **Teams通知**：定期実行タスクで上記を検知し、**Teamsのチャネル/チャットにリマインド投稿**（アプリを開かなくても気づける）。頻度は日次など運用に合わせて設定。
- ※Teams通知・日次バックアップは、対象データ（JSON/Excel）が定期タスクからアクセスできる場所（Box）にあることが前提です。

### G. 維持したい機能（10〜12）

- **複数ソート（10）**：一覧で複数列の優先順位ソートに対応。Excel書き戻し後も、Excel側の標準ソート機能はそのまま使えます。
- **見出しセルの色：1・2行目（11）**：Excel書き戻し時に**ヘッダー2行の塗り色を再現**（プログラムでセル塗り指定するため、この書式は確実に再現できます）。
- **M列 Backlogリンク（12）**：アプリではカード内で**クリック可能なリンク**として表示。Excel書き戻し時も**セルのハイパーリンクを再現**します。

> 補足：Excelの**任意の数式・条件付き書式・入力規則**までは書き戻しで完全再現できませんが、**今回維持したい「見出し色」と「Backlogリンク」は再現可能**です。

## 5. 画面設計（施策管理タブ）

### 5-1. 一覧ビュー
- 事業（全社/UN/SCH/MED/IS）・期間の共通フィルタを流用。
- **複数列ソート**、テキスト検索、大分類/種類/担当/ステータスのフィルタ、**列の表示ON/OFF**。
- 行操作：編集／複製／削除（削除候補）／PDCA設計。ヘッダに「＋新規施策」。
- 上部に**アラート帯**（検証日超過・実績未記入・PDCA停滞・要仕分け）。

### 5-2. 施策カード（1施策＝1画面／横長解消）
- 基本情報：No・大分類・課題目的・手法・施策種類・施策内容・担当・関連施策No・コラム/メルマガ/WP No・事例会社・backlog・優先順位。
- **Backlogリンク**をカード内にクリック可能表示。
- 日付：着手日・公開/配信/実施日・検証日。ステータスはプルダウン。
- **施策タイプ**：単発完了型／継続改善型。
- **KPIセット（最大4組）**：KPI名／目標／実績。「＋KPIを追加」で可変。
- 「最終更新日時」を自動表示（マージの基準）。

### 5-3. PDCA設計パネル
- 検証テンプレ：検証指標（KPIから候補）／判定基準／次アクション。
- 継続改善型は次サイクルを自動生成し、前回実績→今回目標へ引き継ぎ。
- PDCAの結果→施策の実績列へ、次サイクル目標→施策のKPI②以降へ書き戻し（既存TODO 1・3の実現）。

## 6. データモデルの拡張

現行 `shisaku[biz][]` を全列＋新項目に拡張（後方互換：既存フィールドは維持）。

```jsonc
{
  "no": "MED-012",            // 一意・不変（自動採番）
  "daibunrui": "オンラインリード獲得",
  "mokuteki": "サイト流入数増加／CV数増加",
  "kanren": "MED-008",        // D 関連施策No
  "method": "Webサイト／LP改善",
  "cat": "実績事例",           // F 施策種類
  "columnNo": null,           // G
  "mailNo": null,             // H
  "wpNo": null,               // I
  "jireiCompany": "成田赤十字病院様", // J
  "naiyo": "…",
  "tanto": "TM八澤",
  "backlog": "https://…",     // M（リンク）
  "priority": null,           // N
  "status": "完了",
  "shisakuType": "単発完了型",  // 単発完了型 / 継続改善型（PDCA仕分け）
  "startDate": "2024-06-05",  // P 着手日
  "release": "2024-06-05",    // Q
  "check": "2024-09-30",      // R
  "kpiSets": [                // S/T/U, V/W/X, Y/Z/[, \/]（最大4組）
    {"kpi": "コンバージョン率 (CVR)", "goal": "…", "actual": "…"}
  ],
  "pdca": [ /* サイクルごとの検証指標・判定基準・Act・実績 */ ],
  "source": "excel",          // excel / app
  "updatedAt": "2026-07-29T10:00:00+09:00", // 最終更新日時（マージ基準）
  "deleteFlag": false         // 削除候補
}
```

- 旧 `newShisaku`（アプリ内起票）は `shisaku` に統合（`source:"app"`）。
- マスタ（大分類・手法・種類・ステータス等）は「リスト」シートから `masters` に取込。

## 7. 制約・リスク

1. 単一HTML・ファイル運用のため、**同じ行のリアルタイム同時編集は不可**（No.単位のマージで対応。真の同時編集はクラウドDB化が別途必要）。
2. 同期モデル2は**「最終更新日時」列と一意No.の維持が前提**。Excel側でこの列を消す/No.を振り直すとマージが崩れるため、運用ルール化が必要。
3. Excel書き戻しは**維持対象の見出し色・Backlogリンクは再現可能**だが、任意の数式・条件付き書式・入力規則までは再現しない。
4. Teams通知・日次バックアップは**データがBoxにあること**が前提。
5. 既存JSONとの互換は後方互換で確保。

## 9. ご承認・ご判断いただきたい点

1. **フェーズ範囲・順序**：F1（全列取込＋カード表示・複数ソート）から着手でよいか。どこまでを今回スコープに含めるか。
2. **施策No.採番ルール**：事業プレフィックス＋連番（例 `MED-013`）でよいか。既存Noとの整合の取り方。
3. **Teams通知の宛先・頻度**：どのチャネル/チャット宛か、頻度（毎朝など）、通知する条件（期限何日前から等）。
4. **日次バックアップのタイミングと保持世代**：実行時刻（例 毎朝6時）と保持ルール（例 日次30世代＋月初版保存）。
5. **競合解決の運用**：競合時は都度アプリで選択する運用でよいか（自動判定の初期値の希望有無）。
6. **「リスト」マスタの管理主体**：Excelの「リスト」シートを正とするか、アプリ側で管理するか。
