# 実装指示プロンプト：バックアップ自動実行＋Teams通知（F5残り）

対象リポジトリ：`KPI-PDCA`（本体 `KPI-PDCA管理アプリ.html`）／作成：2026-07-29
※この文書は、実装担当（Claude Code等）にそのまま渡す「指示プロンプト」です。仕様の正本は [`docs/KPI-PDCA管理アプリ_仕様書.md`](KPI-PDCA管理アプリ_仕様書.md)（5〜6章）。

---

## 0. ゴール

施策管理アプリの「F5残り」＝**アプリを開いていない/PC電源オフ時でも動く、スケジュール実行のバックアップとTeams通知**を実装する。既存のF1〜F5（施策管理タブ・更新時バックアップ）は**壊さない・作り直さない**。追加分だけを足す。

成果物は次の2層に分かれる（2章）。**両方**を実装対象とする。

- **アプリ内（本リポジトリのHTML/JS）**：設定の編集UI・保存、通知テスト送信、Adaptive Cardの組み立てロジック。
- **クラウド自動化（別基盤／推奨：Power Automate＋Boxコネクタ）**：スケジュール実行、営業日判定、Boxバックアップ、Teams送信。

---

## 1. 前提・現状（重要：壊さないこと）

- 本体は**単一HTML**。データは `<script id="appData" type="application/json">` にJSONで内包。編集→「保存(JSON)」でファイル出力し、Box等の共有場所を更新する運用。
- **更新時バックアップは実装済み（F5）**：`showDirectoryPicker`（File System Access API、Chromium系のみ）で選んだフォルダに、保存のたびに日時付きスナップショットを書き、`pruneBackups()` で世代整理。**このロジックは流用し、重複実装しない。**
- アプリを閉じている時間の自動実行・通知は**未実装**（＝本タスク）。単一HTMLはブラウザを閉じると動けないため、スケジュール部分は**必ずクラウド側**に置く。
- HTMLが巨大＋`appData`行が長大なため、編集は「grepで対象特定→Editでユニーク文字列置換」。全文Readは不可。

---

## 2. アーキテクチャ（分担）

```
┌── アプリ内（HTML/JS・本リポジトリ）──────────────┐     ┌── クラウド自動化（Power Automate等）──────────┐
│ ・通知/バックアップ設定の編集UIと appData保存      │     │ ・スケジュール実行（週次/月次バックアップ・A/B通知）│
│ ・宛先マスタ／チャネルマスタ／休日カレンダー編集   │     │ ・営業日判定（土日＋日本祝日＋会社休業日）        │
│ ・通知ON/OFF                                    │ 読取 │ ・Boxからデータ(JSON)読取／世代整理               │
│ ・通知テスト送信（Webhook/FlowをJSから呼ぶ）      │────▶│ ・トリガー判定→Adaptive Card生成→Teams送信       │
│ ・Adaptive Card生成ロジック（テスト送信と共用）    │     │ ・@メンション/DM/チャネル投稿                     │
└────────────────────────────────────────────────┘     └──────────────────────────────────────────────┘
        設定はappData(JSON)に保存 → Box上のJSONをクラウド側が読む。認証情報はクラウド側のコネクタ/シークレットで保持。
```

- **プラットフォーム選定**：スケジュール層は Power Automate（Boxコネクタ＋Teamsアクション）を推奨（引継ぎ書の想定に一致）。Teamsの「ユーザー@メンション」「チャネル投稿」「アダプティブカード送信」は Power Automate から実現しやすい。Graph API直叩き等でも可だが、要件（@メンション・DM・チャネル）を満たせること。**最終選定はMaya確認**（12章）。
- **設定の受け渡し**：アプリは宛先・休日・ON/OFFを `appData` に保存。クラウド側はBox上の最新JSONからこれらを読む。二重管理を作らない。

## 3. 確定仕様：バックアップ

保存先は**Box（自動で世代バックアップ）**。3系統。

| 系統 | 契機/スケジュール | 世代数 | 実装層 |
|---|---|---|---|
| 更新時 | 「保存(JSON)」実行時 | **30世代**（短期プールへ） | アプリ内（既存流用） |
| 週次 | **毎週月曜 9:30**（休みなら翌営業日） | 短期プールに合流（＝上の30世代を共有） | クラウド |
| 月次 | **毎月1日 9:30**（1日が非営業日なら月初の最初の営業日に1回だけ） | **13世代** | クラウド |

- **世代管理**：短期プール（更新時＋週次）は最新30世代を保持し古い順に削除。月次プールは最新13世代を保持。両者は別フォルダ/別命名で管理（例 `backup/rolling/`・`backup/monthly/`）。
- **月次の重複実行防止**：月初の営業日に1回だけ実行するよう「当月実行済みフラグ」で二重実行を防ぐ（1〜4日を毎日9:30に起動し、条件成立初回のみ実行、等）。
- ファイル命名：`kpi_pdca_backup_YYYY-MM-DD_HHMMSS.json`（既存踏襲）。月次は `..._monthly_...` 等で判別可能に。

> ⚠️ **要確認（12章 A）**：「バックアップ数＝更新30／月次13」の2値のみ指定のため、**週次月曜は短期(30)プールに合流**と解釈した。週次を独立プール（別世代数）にしたい場合は世代数を指定。

## 4. 確定仕様：通知（Teams）

### 種類・頻度・宛先
| 種類 | 頻度 | 宛先 | 形式 |
|---|---|---|---|
| **A：毎朝ダイジェスト** | **毎朝 9:00**（営業日） | **担当者本人＋マネージャー**（人単位・@メンション/DM） | Adaptive Card |
| **B：週次チームサマリー** | **月曜 10:00**（休みなら翌営業日） | **事業チャネルへ全体投稿**（チャネル単位） | Adaptive Card |

- **個人単位（A）とチャネル単位（B）の併用可**。宛先は「人」と「チャネル」の2種別を扱う。

### 通知トリガー（対象施策の抽出条件・A/B共通）
1. **検証日が近い**：検証日 − 本日 ≤ **2日**（未来方向）。
2. **公開後2日で実績未記入**：公開/配信/実施日 ＋2日 を経過し、かつKPI実績が空。
3. **新規施策が着手日超過で未着手**：着手日 ＜ 本日 かつ 状態＝未着手。

各施策に「どのトリガーで該当したか」を付し、カードに表示。

### 社外担当の振替（確定）
- 担当者マスタに **社外フラグ** と **振替先（社内の人・人単位）** を持つ。振替先は「マネージャー または 社内担当者」いずれも人単位で指定可。
- **A通知の宛先ロジック**：
  - 担当が**社内** → 「本人」＋「マネージャー（設定があれば）」。
  - 担当が**社外** → **本人へは送らない**。**振替先のみ**へ送る。
- マネージャー／振替先は各担当者に紐づく人単位フィールドで表現（同一フィールドで兼ねてよい）。

### 通知先の管理（アプリ内・必須）
- **宛先マスタ編集**：氏名／TeamsのUPN（メール）／社外フラグ／マネージャー・振替先（他の人物を参照）。
- **チャネルマスタ編集**：事業（UN/SCH/MED/IS）→ 投稿先Teamsチャネル。
- **ON/OFF**：通知全体、種別（A・B）ごとにON/OFF。
- **通知テスト**：ボタンで、指定宛先へ実際にサンプルAdaptive Cardを即送信し、見た目・宛先・メンションを運用前に確認できる（クラウド側のテスト用エンドポイント/FlowをJSから呼ぶ）。

## 5. 営業日・休日カレンダーのロジック（確定）

- **休日 ＝ 土日 ＋ 日本の祝日（自動判定）＋ 会社独自の休業日（アプリに登録）**。
- 会社休業日は**アプリ内で登録・編集**（夏季/年末年始等）。`appData` に保存し、クラウド側が参照。
- **翌営業日ロジック**：
  - 週次バックアップ（月曜9:30）／週次通知B（月曜10:00）：その月曜が休日なら**翌営業日**の同時刻に実行。
  - 月次バックアップ（1日9:30）：1日が非営業日なら**その月の最初の営業日**に1回だけ実行。
- 毎朝通知A（9:00）：**営業日のみ**送信（休日は送らない）。※12章Bで最終確認。

## 8. Teams Adaptive Card 仕様

- 構成：**見出し**（種類・対象日・事業）＋**対象施策の一覧**（各行：施策No／施策内容／事業／トリガー種別／検証日 or 公開日／担当）＋**各施策のリンク**（backlog URL 等、無ければアプリ該当箇所への導線）。
- A：宛先個人にメンション（社外は振替先）。件数多い日は「上位N件＋残り○件」に丸める。
- B：事業チャネルへ投稿し、事業単位のサマリー（該当件数・内訳）を表示。
- カード生成ロジックはアプリ内（テスト送信）とクラウド側（本番送信）で**同一の組み立て規則**にする（仕様を1箇所に定義し двух重化しない）。

## 9. 設定・シークレット

- Box：バックアップ保存先フォルダ、読取（データJSON）。認証はクラウドコネクタ側。
- Teams送信：Power Automate（Teamsアクション）または Graph API。@メンション・DM・チャネル投稿・Adaptive Card送信に対応できる方式を選ぶ。
- シークレット（Boxトークン/Flow URL等）は**HTMLに直書きしない**。クラウド側で保持し、アプリからはテスト用Flow URL（`webhookTestUrl`）のみ参照。

## 10. 受入基準（テスト）

- **バックアップ**：(1) 更新時＝保存で短期プールに追加され30超で最古が削除。(2) 週次月曜が休日→翌営業日に実行。(3) 月次1日が休日→月初営業日に1回だけ実行、二重実行なし。(4) 月次13世代維持。
- **通知**：(1) 3トリガーが正しく施策を抽出（境界値：検証日ちょうど2日前が含まれる、公開後ちょうど2日 等）。(2) A＝担当社内は本人＋マネージャー、社外は振替先のみ・本人へ送らない。(3) B＝事業チャネルへ投稿。(4) ON/OFFが効く。(5) テスト送信が実際に届き、プレビューと一致。(6) 宛先未設定の担当は警告一覧に出る（無言スキップ禁止）。
- **回帰**：既存F1〜F5が壊れていない（施策CRUD・Excel相互マージ・更新時バックアップ・PDCA足場）。
- **検証手段**：本セッションはNode/Pythonが使えるため、アプリ内ロジック（トリガー判定・営業日判定・宛先解決・カード生成）は `node --check`＋jsdomで単体検証する。クラウド側はテスト送信で疎通確認。
